# 관리자 웹서버 연동 규격 초안 (담당 팀 협의용)

> 작성: 2026-08-31 · 상태: **초안** — 관리자 웹 담당 팀과 협의 후 확정
> 배경: 2026-08-31 회의 결정 — **관리자 화면 전체를 별도 웹서버로 다른 팀·업체가 구현**하고,
> **사용자·참여 기록 데이터를 웹서버가 소유**한다. Unity(게임)는 API로 조회·저장한다.
> **2026-10-07 결정:** 서버는 **외부 서버**(P1 → 기획 문서 개정 필요) · 로그인은 **기관·운영자 단위**(어르신 개인 로그인 없음) · ERD는 게임 개발 측이 정해 서버 팀에 전달 → **`93_서버_ERD_초안.md`** (API 표 갱신 · 오프라인 폴백 = P2 답 포함)

| # | 확인 사항 | 관련 확정 조항 |
|---|---|---|

## 1. Unity → 서버 (Unity가 호출하는 API)

게임이 서버에 요구하는 최소 3종. 프로토콜은 HTTP+JSON 가정(협의).

| # | 용도 | 시점 | 필요 데이터 |
|---|---|---|---|
| A1 | **사용자 목록 조회** | SCR-003 진입 시 | id · 이름(≤5자) · 성별(남/여) · 아바타 번호(0~7) · 카드 배경색 번호(0~7) |
| A2 | **참여 기록 저장** | 게임 10라운드 완주 시(중도 종료·비회원은 호출 안 함) | 아래 2장 PlayRecord 스키마 |
| A3 | **참여 기록 조회(1인)** | SCR-023 내 기록 보기 진입 시 | 해당 사용자의 PlayRecord 목록 (최근 5회 평균·최근 5건 계산은 Unity가 함 — 또는 서버 집계 제공, 협의) |

- 응답 지연 허용: SCR-003·023은 화면 진입 시 1회 호출 — 1초 내 응답 희망.
- A2 실패 시 재시도·로컬 보관 후 재전송 여부는 P2 정책과 함께 협의.

## 2. 참여 기록 데이터 스키마 (현행 Unity 구조 — 서버 DB 설계 참고)

현재 Unity가 쌓는 구조(`Assets/Scripts/Save/SaveModels.cs`). 필드 의미는 03 문서 FN-22 · 07 문서 4-8/5-14/6-9 확정 항목과 일치한다.

## 3. 서버/관리자 화면 → Unity (Unity가 제공해야 하는 것)

관리자 화면 기능 중 **Unity만 알 수 있거나 Unity만 할 수 있는 것**. 제공 방식(Unity가 소형 상태 API를 열지, 서버로 주기 push할지)은 협의.

| # | 항목 | 근거 | 내용 |
|---|---|---|---|
| B1 | 점검 상태 | ADM-001 · REF-A-02 | 카메라 연결 여부 · 사람 인식 여부(추적 파이프라인 상태). 저장 공간·날짜 시각은 같은 PC라면 서버가 자체 확인 가능 |
| B2 | 카메라 미리보기 | ADM-001 (조건부 · C7) | 웹캠 프레임 스냅샷 0.5초 간격 — Unity가 카메라를 점유하므로 Unity 제공 필수 |
| B3 | 프로그램 종료 | ADM-008 끝내기 3종 | 「프로그램 종료」는 사용자 화면(Unity)까지 종료 — Unity에 종료 명령 전달 필요 |
| B4 | 소리 설정 반영 | ADM-008 | 소리 크기 3단계 · 음성 안내 on/off를 Unity 재생에 적용 (음성 도입 시) |

## 4. Unity 측 작업 계획 (규격 확정 후)

- 현행 로컬 저장(`SaveStore`)의 **호출 지점은 4곳뿐** — FlowManager.CommitPlay(저장) · SCR-003(사용자 목록) · SCR-023(기록 조회) · 관리 없음. 내부 구현만 API 클라이언트로 교체하면 화면·게임 코드는 그대로다.
- 규격 확정 전까지는 로컬 저장을 유지한다(개발·검증용). P2 결정에 따라 로컬을 폴백으로 남길지 정한다.
